# Project page, components and connections

## Project page

From the console, the open-page button on the right end of any project header in the navigator (shown while browsing **All work** or a company) goes straight to that project's page; the rest of the header still folds its tasks. The project page is one row of tabs over a page that fills the window and scrolls on its own: **Blueprint**, **Sections** and **Deployment graphs** (what is written about the project), **Components** and **Connections** (what it is made of and what it reaches), and **Settings** (the **Description**, the **Folder** and **Commit on claim**). A tab shows how many its page holds, and **Connections** carries an amber dot while a binding has no credential. **Components** lists the folders of the project that are parts of it: a name, a folder and a description each, added from **Add component** (the name starts as the folder's own name, and **Browse** opens the editor's path picker, listing folders only, to choose it). They are drawn as the tree their folders form under the project's folder, one line each, grouped under their parent folder (`billing/`), with the ones outside it under their own heading; a filter narrows the tree by name, folder or description. One opens at a time in an editor beside the tree, with autosave, moved up or down, or deleted behind a confirm. Names are unique on a project, ignoring case. Every context that loads the project, from its own anchor or through one of its tasks, carries them in a `<components>` block, so a session told "the billing module" knows which folder that is and what it does; only the console writes them. A task description or a step detail can name one as `[[Component name]]` (matched ignoring case): the text stays as written, and the context a session reads carries the component's name, folder and description at the first mention, name and folder after, and a `component not found in this project` line for a name that matches nothing. References inside code spans and fenced blocks are left alone. In the console the markdown stays as written; read mode draws a reference in a task description or a step detail as a chip whose hover shows the component's folder and description, and a name the project does not have as a struck-through red chip (the chips follow a rename without a reload). Write mode shows the source as typed, and text with no project, such as a note, keeps its brackets. The **Blueprint** tab holds what every `/rk` hands to Claude; the **Sections** tab lists the project's sections beside the one open. A section is a title and markdown, written from the **+** above that list, edited in place with autosave, moved up or down, or deleted behind a confirm. Titles are unique on a project, ignoring case. Sections are never part of any context, so they cost no tokens and a session reads them only with `rekall_read_sections` (a list of titles, then one section by title) or if you paste one in; a session adds one with `rekall_project_section`, starting from the task it works (`/rk project:vega task:report-builder section "Deployment" "how we ship"` asks for exactly that, and so does a step such as "document X in a section named Y"), and it appears in the list without a reload.

A project wears an **icon**: one of the fixed glyphs, or a picture of your own, both set in the project's edit dialog (**Upload image** takes a PNG, JPEG, WebP or GIF up to 10 MB). Whatever its shape, a picture is cropped to the centred square and shown with the rounded corners of a macOS icon, in the project cards and header, the console's task column and the project picker of the New task dialog. The server keeps one 512 px PNG master per project (`project_icon_image`; a smaller upload is not enlarged) and resizes it with Lanczos3 on premultiplied alpha to exactly the device pixels each spot asks for (`GET /api/projects/{id}/icon-image?size=N&v=<version>`, 8 to 512; with `v` the answer is cached for good, and `iconImageVersion` on the project changes with every upload). `PUT` takes the image file as the body and answers the project; `DELETE` takes the picture off and the glyph returns.

A company wears a **logo** the same way, uploaded from the company's edit dialog (**Logo**, same formats and limit). The console's scope picker shows it on its closed trigger whenever that company or one of its projects is in scope (with a project, the project's icon sits on the logo's corner), and beside each company in the open list; **All work** keeps its own glyph. Without a logo a company wears its initial on its identity colour. The server stores and renders it exactly like a project picture (`company_logo_image`; `GET`, `PUT` and `DELETE /api/companies/{id}/logo-image`, with `logoImageVersion` on the company).

The project's tasks are not listed on the page: **Tasks** in the header opens them in a panel from the right, each with an **Open** that takes you to it in the console. The REST side is `GET` and `POST /api/projects/{id}/sections`, `PUT /api/projects/{id}/sections/order` (every section id once, in the order to show) and `PUT` and `DELETE /api/project-sections/{id}`. Components are `GET` and `POST /api/projects/{id}/components`, `PUT /api/projects/{id}/components/order` (every component id once) and `PUT` and `DELETE /api/project-components/{id}`.

A company holds **connections**: the GitLab instances, Kubernetes clusters and Jira sites its projects reach. They live on the company's **Connections** screen (`/companies/:id/connections`, the plug button on each company in the company list): a GitLab, a Kubernetes and a Jira group, each under its system's logo with its count, how many lack a credential and its own **+ Add**, listing each connection's label, address (the instance host, or the cluster's context and server) and whether a credential is stored, and beside them the selected connection in full. There you create one (kind, title, label, the instance URL for GitLab or the site URL for Jira and, for a network that reaches Jira only through one, the proxy its calls go through, and optionally its credential), replace or clear its credential, **Check now**, see which projects use it, read its access log (every request a terminal made for the credential, handed out or refused and why) and delete it, which says how many projects lose it. A kubeconfig is pasted or picked as a file, its contexts are listed with how each logs in, the ones Rekall cannot use are shown with why, and you choose the one to keep. A connection's credential (a GitLab personal access token, a kubeconfig reduced to the one context you choose, or for Jira, a Cloud account's email and API token or a Data Center personal access token) is kept in the operating system's credential store (the macOS Keychain, the Windows Credential Manager, or on Linux the kernel keyring, which forgets it when you log out), never in the database, and nothing ever sends it back: the console only learns when it was set. Rekall reads each credential from that store once per launch and keeps it in memory, so the macOS Keychain asks for your password at most once per connection each time Rekall starts. Answering **Always Allow** stops even that, until the app is rebuilt: a build signed ad hoc is a new application to the Keychain. A kubeconfig whose user logs in by running a command (cloud CLIs), with a username and password, against a server that is not `https://` or skips TLS verification, or through a `proxy-url` that is not `http://`/`https://` or carries a password is refused on import; a cluster's `proxy-url` is kept, and both the check and the terminal's `kubectl` go through it. A project binds the connections it uses, each with a label and an optional target (the GitLab project path, the namespace or the Jira project key), from the **Connections** tab of its page. There each company connection the project uses heads a line, in its system's colour, with its host and whether a credential is stored, and every binding hangs off that line as a label and a target edited in place, with a cross to stop using it. **+ Target** binds the same connection once more, the company's other connections wait below with **Use**, **New connection** creates one and binds it, and a filter narrows the bindings by label or target. One connection can be bound several times, once per target, so a GitLab token configured once reaches every repository of a multi-repository project, each under its own label. **Find repositories**, on a project with a folder, does that in one go: it looks for git repositories under the folder (a repository is not searched further, so a submodule is not listed), reads each one's `origin`, binds every one whose origin is on a GitLab connection of the company with a token, labelled after its folder, and adds a component named after the folder when none has it. A second clone of the same GitLab project is recognised as already connected. The result lists each repository with what became of it, including the ones left out: no origin, no GitLab connection for its host, or a connection with no token. A used connection without a credential is flagged, since a session on that project is told the same. A **check** asks GitLab, the cluster or Jira whether the stored credential still works and says who it signs in as, or why it does not. A terminal opened with **Run here** on a project that binds connections can use them without ever holding the credential: `kubectl --context <label>` reaches the cluster, `git push` to the GitLab host over HTTPS is authenticated, `rekall-gitlab --connection <label> GET /projects/:project/pipelines` calls the GitLab API (the label is the binding's, and `:project` its project path), and `rekall-jira --connection <label> POST /issue -d '{…}'` creates a Jira issue. Each asks Rekall for the credential through a helper that only works while that terminal is open, and every request is logged against the connection. The terminal pane and the sessions panel show a chip per connection the session has used, counting each hand-out as it happens and turning amber when a request was refused; the ones it has not used yet fold into one **N unused** chip that opens to list them (amber when no credential is stored), and a connection leaves it the first time it is used. Connections are listed by kind, clusters first, then GitLab, then Jira. A task description or a step detail can name a binding as `[[connection:label]]`, offered by the same `[[` completion as components: read mode draws it as a chip whose hover shows the connection's kind, title and target (struck through in red when the project binds no such label), and the context a session reads names the binding and points it at its line in `<connections>`. This needs `curl` and a Unix shell, so it is not available on Windows, and a terminal opened with **Open in terminal** gets none of it. A Jira connection a project binds with its project key and a credential also offers **Import issues as tasks** on the project's page: it lists the project's 50 most recently updated open issues, and each one you pick becomes a task labelled with its key (`eng-12`), titled with its summary, its description carried over below a link back to the issue. An issue already imported is shown as such and is not imported twice. The REST side is described in [docs/design/write-safety.md](../design/write-safety.md).
