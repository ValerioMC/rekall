# Project page, components and connections

## Project page

From the console, the open-page button on the right end of any project header in the navigator (shown while browsing **All work** or a company) goes straight to that project's page; the rest of the header still folds its tasks. The project page is one row of tabs over a page that fills the window and scrolls on its own: **Blueprint**, **Sections** and **Deployment graphs** (what is written about the project), **Components** and **Connections** (what it is made of and what it reaches), and **Settings**, a rail of four panes beside the one open: **General** (the title, the label and the anchor they make, the task key that opens its tasks' codes, the company, the status, the icon, the description and **Delete project**, saved together with **Save** since a new label moves the anchor), **Repository** (the **Folder**, the **Main branch**, **Merge through a pull request** and **Commit on claim**), **Task manager** (which of the project's GitLab, GitHub or Jira bindings its tasks are written to) and **Checks** (**Done when**). **Main branch** is the branch a task's own branch starts from and is merged into once its work is accepted; left empty it is whichever branch the folder is on, and a merge waits while the folder is on another one. **Merge through a pull request** is off unless it is switched on (what it does is in [workflow](workflow.md): the branch is pushed and a pull request, or a GitLab merge request, opened when the task's work is claimed, and accepting the task merges it with a merge commit, closes the issue and removes the worktree; a conflict opens a merge session), and a project can switch it on only with a folder, a main branch (or a folder on a git branch) and a GitHub or GitLab task manager; a Jira one has no pull requests. The save is refused with the missing piece named, and while it is on, choosing a Jira binding as the task manager, unchecking the task manager or removing its binding is refused the same way until the switch is turned off. **Task manager** picks at most one binding, which needs a target (the GitLab project path, the GitHub `owner/repo` or the Jira project key) and a stored credential: from then on a plain task created in the project, by the console or by a session, creates an issue there with its title alone, assigned to the user the stored credential belongs to and typed as a task (GitHub and GitLab fall back to an untyped issue when the repository has no such type; Jira's project is the binding's target). Nothing writes the issue again on its own, so its history holds one entry per sync instead of one per edit: the sync key beside the issue's link writes the task's title and description when pressed (a quick task and an epic are never written). Deleting the task deletes the issue (GitHub, which lets only an administrator delete one, closes it as not planned otherwise; a failure is logged). The task shows the sync key beside its title and the issue's link right after it, which opens in the browser from the desktop app too: a dot on the key says the task changed since the issue was written, the key spins while it writes and becomes a check when the issue is current, and **Not synced** with the reason appears when the last write failed, which pressing the key again retries (on a task with no issue yet, because creating it failed, the key creates it); a task that existed before the choice, or one synced before the key existed, shows the dot until it is pressed once, and an issue imported from the task manager's own Jira project is the task's issue already and is not written back. A project with a task manager also keeps every queued task on a branch of its own, in a worktree, even when only one session runs at a time. A tab shows how many its page holds, and **Connections** carries an amber dot while a binding has no credential. **Components** lists the folders of the project that are parts of it: a name, a folder and a description each, added from **Add component** (the name starts as the folder's own name, and **Browse** opens the editor's path picker, listing folders only, to choose it). They are drawn as the tree their folders form under the project's folder, one line each, grouped under their parent folder (`billing/`), with the ones outside it under their own heading; a filter narrows the tree by name, folder or description. One opens at a time in an editor beside the tree, with autosave, moved up or down, or deleted behind a confirm. Names are unique on a project, ignoring case. Every context that loads the project, from its own anchor or through one of its tasks, carries them in a `<components>` block, so a session told "the billing module" knows which folder that is and what it does; only the console writes them. A task description or a step detail can name one as `[[Component name]]` (matched ignoring case): the text stays as written, and the context a session reads carries the component's name, folder and description at the first mention, name and folder after, and a `component not found in this project` line for a name that matches nothing. References inside code spans and fenced blocks are left alone. In the console the markdown stays as written; read mode draws a reference in a task description or a step detail as a chip whose hover shows the component's folder and description, and a name the project does not have as a struck-through red chip (the chips follow a rename without a reload). Write mode shows the source as typed, and text with no project, such as a note, keeps its brackets. The **Blueprint** tab holds what every `/rk` hands to Claude; the **Sections** tab lists the project's sections beside the one open. A section is a title and markdown, written from the **+** above that list, edited in place with autosave, moved up or down, or deleted behind a confirm. Titles are unique on a project, ignoring case. A context carries only their titles, in a `<sections>` block, so a section costs a line and a session reads it with `rekall_read_sections` (a list of titles, then one section by title) when the work touches it; a session adds one with `rekall_project_section`, starting from the task it works (`/rk task:VG-12 section "Deployment" "how we ship"` asks for exactly that, and so does a step such as "document X in a section named Y"), and it appears in the list without a reload. The sparkle beside **+** is **Autoconfigure**: it opens a session on the project (`/rk project:<label> autoconfigure`) that finds the project's upstream repository (a GitHub or GitLab binding, the folder's `origin`, or a URL in its description), reads what it publishes (README, `CONTRIBUTING`, the issue and pull request templates, CI, a few merged pull requests) and writes `Overview`, `Contributing`, `Development` and, when the project says how it releases, `Release`. `Contributing` is the procedure from an issue to a merged change, with the exact `rekall-github` or `rekall-gitlab` call for the issue and the pull request and every field the project lets be decided in advance; since every context names it, a later session on the project follows it when it files an issue, names a branch or opens a pull request. A section that already exists is rewritten keeping what it says that is still true.

A project wears an **icon**: one of the fixed glyphs, or a picture of your own, both set in the project's edit dialog (**Upload image** takes a PNG, JPEG, WebP or GIF up to 10 MB). Whatever its shape, a picture is cropped to the centred square and shown with the rounded corners of a macOS icon, in the project cards and header, the console's task column and the project picker of the New task dialog. The server keeps one 512 px PNG master per project (`project_icon_image`; a smaller upload is not enlarged) and resizes it with Lanczos3 on premultiplied alpha to exactly the device pixels each spot asks for (`GET /api/projects/{id}/icon-image?size=N&v=<version>`, 8 to 512; with `v` the answer is cached for good, and `iconImageVersion` on the project changes with every upload). `PUT` takes the image file as the body and answers the project; `DELETE` takes the picture off and the glyph returns.

A company wears a **logo** the same way, uploaded from the company's edit dialog (**Logo**, same formats and limit). The console's scope picker shows it on its closed trigger whenever that company or one of its projects is in scope (with a project, the project's icon sits on the logo's corner), and beside each company in the open list; **All work** keeps its own glyph. Without a logo a company wears its initial on its identity colour. The server stores and renders it exactly like a project picture (`company_logo_image`; `GET`, `PUT` and `DELETE /api/companies/{id}/logo-image`, with `logoImageVersion` on the company).

The project's tasks are not listed on the page: **Tasks** in the header opens them in a panel from the right, each with an **Open** that takes you to it in the console. The REST side is `GET` and `POST /api/projects/{id}/sections`, `PUT /api/projects/{id}/sections/order` (every section id once, in the order to show) and `PUT` and `DELETE /api/project-sections/{id}`. Components are `GET` and `POST /api/projects/{id}/components`, `PUT /api/projects/{id}/components/order` (every component id once) and `PUT` and `DELETE /api/project-components/{id}`. Checks are `GET` and `POST /api/projects/{id}/checks`, `PUT /api/projects/{id}/checks/order` (every check id of the project's own scope once), `POST /api/steps/{id}/checks` with `PUT /api/steps/{id}/checks/order` for one step's, `PUT` and `DELETE /api/checks/{id}`, and `GET /api/tasks/{id}/check-results` for what their runs found, the latest first.

**Connections** are the GitLab instances, GitHub servers, Kubernetes clusters, Jira sites and Grafana instances projects reach. A connection belongs to the workspace, not to one company: it is **shared with** the companies whose projects may use it, so one GitHub account, or one GitLab token, serves several companies, and a project can bind only a connection shared with its company. A GitLab or GitHub connection may name a **root path**, the group, namespace or owner its token covers (`acme/platform`, `vmcforge`). They live on the **Connections** screen (`/connections`, the third entry of the **Catalog** menu beside Projects and Companies): a list grouped by kind, Kubernetes first, then GitLab, GitHub, Jira and Grafana, each under its system's logo with its count, and beside it the selected connection in full. Each row shows the connection's title, what it covers (the instance host and root path, or the cluster's context and server), whether a credential is stored (a tick, a warning triangle once a check failed, or an empty ring, always with its word), and how many companies and projects use it; one shared with no company is flagged **Not shared with any company**. Three filters narrow the list by company (connections shared with it), kind and status (needs a credential, not shared with any company), and the selection and filters live in the address. **New connection** opens a sheet: the kind first (fixed afterwards), then the title, the instance URL for GitLab, the server URL for GitHub (`https://github.com`, or a GitHub Enterprise Server's address) the site URL for Jira or the instance URL for Grafana, the root path for GitLab and GitHub, for a network that reaches Jira or Grafana only through one the proxy its calls go through (Check, the terminal helper and, on Jira, the issue import all use it), for a Grafana instance that serves a self-signed certificate a checkbox to accept it (Check and `rekall-grafana` then skip verifying the certificate), optionally the credential, and the companies it is shared with; the label sessions name it by sits under **Label and advanced settings** and is made from the title; with no company ticked the sheet says the connection is not shared yet and no project can use it. The selected connection shows its address, its **Credential** (add, replace or remove it, and **Check**, which says whether it still works and when it was asked; with none stored the panel says so and offers only to add one), **Shared with** (each company the connection is shared with and, under it, the projects that bind it with their target and **Unbind**, which asks before it acts; **Edit companies** changes the set, and a company whose projects still bind the connection stays locked, with a lock in place of its checkbox and the projects named as links, until they are unbound; **Save companies** waits for a change) and its **Access log** (every request a terminal made for the credential, handed out or refused and why). **Delete** says first which companies it is shared with, which projects it is unbound from and that its stored credential goes with it. With a company filtered that has no connection, the empty list offers **New connection for** that company. A kubeconfig is pasted or picked as a file, its contexts are listed with how each logs in, the ones Rekall cannot use are shown with why, and you choose the one to keep. A connection's credential (a GitLab or GitHub personal access token, a kubeconfig reduced to the one context you choose, for Jira, a Cloud account's email and API token or a Data Center personal access token, or for Grafana, a service account token or the user and password of an account) is kept in Rekall's own credential file (`secrets.json` in Rekall's home folder, readable by your user only and not encrypted), never in the database, and nothing ever sends it back: the console only learns when it was set. Rekall never asks the operating system's credential store for it, so the macOS Keychain does not prompt. A credential an earlier version saved in the Keychain is read from it once, the first time it is needed (the one prompt left), and copied into the file; deleting a credential removes both copies. A kubeconfig whose user logs in by running a command (cloud CLIs), with a username and password, against a server that is not `https://` or skips TLS verification, or through a `proxy-url` that is not `http://`/`https://` or carries a password is refused on import; a cluster's `proxy-url` is kept, and both the check and the terminal's `kubectl` go through it. A project binds the connections it uses, each with a label and an optional target (the GitLab project path, the GitHub `owner/repo`, the namespace, the Jira project key or the Grafana folder UID), from the **Connections** tab of its page. That tab only binds: it never edits a credential, runs a check or changes who a connection is shared with. Each connection the project uses heads a line, in its system's colour, with its host, whether a credential is stored and an **Open in Connections** link to it (the hub then offers a way back to the project), and every binding hangs off that line as a label and a target edited in place, with an **Unbind** that asks before it acts. When a connection covers a root path and a target does not start with it, the row says what it expected (`Expected to start with acme/`); the target is still saved. **+ Target** binds the same connection once more, the connections shared with the project's company that it does not use wait below, in kind order, with their scope and credential state and a **Bind** button (one with no credential says so and links to it in Connections), and a line counts the connections that exist but are not shared with the company, **New connection** opens the same sheet as the hub, which says it will be shared with the project's company and bound to the project and, once saved, binds the new connection to the project and leaves you on the tab (if the binding fails, the connection stays and the message says it was created but not bound), and, from eight bindings, a filter narrows them by label or target. When no connection is shared with the company yet, the tab says so and offers **New connection** or a link to the hub filtered to that company; **Manage connections** in the tab's header links there too. The company list shows, on each company, a link counting the connections shared with it (`3 connections`, or `No connections`) that opens the hub filtered to it, and the old `/companies/:id/connections` address redirects there. One connection can be bound several times, once per target, so a GitLab token configured once reaches every repository of a multi-repository project, each under its own label. **Find repositories**, on a project with a folder, does that in one go: it looks for git repositories under the folder (a repository is not searched further, so a submodule is not listed), reads each one's `origin`, binds every one whose origin is on a GitLab or GitHub connection shared with the company that has a token (when several match, the one whose root path covers the most of the repository's path wins, then one with a token), labelled after its folder, and adds a component named after the folder when none has it. A second clone of the same GitLab project is recognised as already connected. The result lists each repository with what became of it, including the ones left out: no origin, no GitLab or GitHub connection for its host, or a connection with no token. A used connection without a credential is flagged, since a session on that project is told the same. A **check** asks GitLab, GitHub, the cluster, Jira or Grafana whether the stored credential still works and says who it signs in as, or why it does not. A terminal opened with **Run here** on a project that binds connections can use them without ever holding the credential: `kubectl --context <label>` reaches the cluster, `git push` to the GitLab or GitHub host over HTTPS is authenticated, `rekall-gitlab --connection <label> GET /projects/:project/pipelines` calls the GitLab API (the label is the binding's, and `:project` its project path), `rekall-github --connection <label> POST /repos/:project/issues -d '{…}'` files a GitHub issue (`:project` is the `owner/repo`) and `POST /repos/:project/pulls` opens a pull request, `rekall-jira --connection <label> POST /issue -d '{…}'` creates a Jira issue, and `rekall-grafana --connection <label> GET /search?query=…` finds Grafana dashboards. Each asks Rekall for the credential through a helper that only works while that terminal is open, and every request is logged against the connection. The terminal pane and the sessions panel show a chip per connection the session has used, counting each hand-out as it happens and turning amber when a request was refused; the ones it has not used yet fold into one **N unused** chip that opens to list them (amber when no credential is stored), and a connection leaves it the first time it is used. Connections are listed by kind, Kubernetes first, then GitLab, GitHub, Jira, then Grafana. A task description or a step detail can name a binding as `[[connection:label]]`, offered by the same `[[` completion as components: read mode draws it as a chip whose hover shows the connection's kind, title and target (struck through in red when the project binds no such label), and the context a session reads names the binding and points it at its line in `<connections>`. This needs `curl` and a Unix shell, so it is not available on Windows, and a terminal opened with **Open in terminal** gets none of it. A Jira connection a project binds with its project key and a credential also offers **Import issues as tasks** on the project's page: it lists the project's 50 most recently updated open issues, and each one you pick becomes a task labelled with its key (`eng-12`), titled with its summary, its description carried over below a link back to the issue. An issue already imported is shown as such and is not imported twice. The REST side is described in [docs/design/write-safety.md](../design/write-safety.md).

**Done when** lists the commands run before a step's claim is accepted: a name, the command, a folder inside the project's folder (empty runs in the folder itself) and a timeout in seconds. Checks are added, edited, moved up or down and deleted there; a project with none behaves as it did. A step's detail has its own **Done when** for checks that apply to that step alone. While a claim is refused, or after it passes, the step shows what each check found: passed or failed with its exit code or a timeout, how long it took and when, and the end of its output, open on the failed ones. The results appear while the session is still working. A project with checks and no folder is flagged, because a claim is refused without one.
